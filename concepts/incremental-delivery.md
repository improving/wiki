# incremental delivery

Incremental delivery means shipping small, complete slices of value frequently rather than accumulating work toward a big-bang release. In this corpus the test of an increment is usability: each slice must deliver something real to users, so feedback and learning begin earlier and momentum builds.

## Key Claims

- An Increment must deliver value to end users: if users notice no change at the end of a sprint, no increment was delivered; splitting a feature by layer (API then UI) delivers no usable value in the first sprint ([Transformative Insights](/sources/transformative-insights-enhancing-development-effectiveness-through.md)).
- Delivering an end-to-end slice each sprint enables earlier feedback and faster pivots, and made a mid-stream handoff painless because delivered work was self-contained ([Transformative Insights](/sources/transformative-insights-enhancing-development-effectiveness-through.md)).
- Scope for a 12-week win that delivers measurable value within three months, then let each phase fund the next ([Overambitious Scope](/sources/overambitious-scope.md)).
- Release as often as possible: a backlog is a set of hypotheses, and delay postpones both learning and value ([When Should We Release In Scrum?](/sources/when-should-we-release-in-scrum.md)).
- One client moved from annual to quarterly releases — real progress even short of full continuous delivery ([When Should We Release In Scrum?](/sources/when-should-we-release-in-scrum.md)).
- The Agile Manifesto's principles prioritize early and continuous delivery of valuable software ([The Manifesto for Agile Software Development](/sources/the-manifesto-for-agile-software-development.md)).
- Turning one idea into a real, done product update in a single focused Sprint converts skeptics into advocates and creates hunger for more ([Struggling to Deliver Done Work, Part 1](/sources/struggling-to-deliver-done-work-every-sprint-part-1-dependencies.md)).
